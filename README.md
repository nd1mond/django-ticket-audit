# Аудит Django-приложения обработки заявок

Анализ незнакомого веб-приложения (helpdesk-система заявок): восстановление архитектуры и бизнес-логики, поиск уязвимостей и дефектов, исправления и регрессионные тесты.

**Стек:** Python, Django, SQLite, Django ORM, unit-тесты (`django.test`)

## Что это за приложение

Система заявок с тремя ролями:

| Роль | Что должна уметь |
|---|---|
| Пользователь | создавать заявки, видеть и редактировать свои, видеть публичные |
| Модератор | видеть все заявки, включая приватные, менять статусы |
| Администратор | всё выше + удаление заявок и административная консоль |

Сущности: заявки (с приоритетом, статусом и признаком приватности), комментарии, вложения, профили пользователей.

## Ход работы

1. **Инвентаризация.** Запуск проекта, фиксация моделей, URL-маршрутов, форм, ролей и ключевых пользовательских сценариев.
2. **Реверс-инжиниринг бизнес-логики.** Матрица прав «роль × действие» по 15 сценариям в двух вариантах: как реализовано фактически и как должно работать.
3. **Поиск проблем.** Проверка кода, форм, шаблонов, настроек и поведения для разных ролей.
4. **Исправления и тесты.** Каждое исправление подтверждено автотестами без поломки существующей функциональности.

## Главная находка

Фактическая матрица прав показала, что роли почти не участвуют в контроле доступа: **любой авторизованный пользователь** мог видеть чужие приватные заявки, редактировать и удалять их, менять статусы, скачивать чужие вложения и назначить себе роль администратора через форму профиля.

## Найденные проблемы

**Уязвимости (SEC-01 – SEC-07)**

| ID | Проблема | Категория |
|---|---|---|
| SEC-01 | Доступ к чужим и приватным заявкам | Broken Access Control |
| SEC-02 | Редактирование чужих заявок | Broken Access Control |
| SEC-03 | Удаление заявок через GET-запрос (подделка запроса со стороннего сайта) | Broken Access Control / CSRF |
| SEC-04 | SQL-инъекция в поиске заявок (сырой SQL через f-string) | SQL Injection |
| SEC-05 | Повышение привилегий через редактирование профиля (поле `role` в форме) | Mass Assignment / Privilege Escalation |
| SEC-06 | Изменение статуса заявки обычным пользователем | Mass Assignment / бизнес-логика |
| SEC-07 | Выполнение скриптов в комментариях | Cross-Site Scripting (XSS) |

**Дефекты качества (BUG-08 – BUG-17):** функциональные ошибки и ошибки UX, производительность запросов, качество кода.

## Ключевые исправления

- Единые функции проверки прав: `can_view_ticket`, `can_edit_ticket`, `can_delete_ticket`, `accessible_tickets_for`. Список и карточка заявки показывают только то, что разрешено роли.
- Поле `role` убрано из формы профиля, поле `status` — из пользовательской формы заявки. Статус меняют только модератор и администратор.
- Удаление заявки только через `POST` (`@require_POST`) с проверкой прав.
- Сырой SQL в поиске заменён на безопасный запрос Django ORM.
- Экранирование пользовательского ввода в шаблонах.
- **Устранена проблема N+1:** `select_related('owner')` и `prefetch_related('comments__author', 'attachments')` вместо отдельного запроса к базе на каждую заявку.

## Тесты

Регрессионные тесты в `tickets/tests.py`:

- пользователь не может открыть чужую приватную заявку;
- пользователь не может отредактировать чужую заявку;
- пользователь не может назначить себе роль администратора;
- HTML в комментариях экранируется (защита от XSS).

```bash
python manage.py test tickets
```

## Запуск

```bash
python -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\activate
pip install -r requirements.txt
python manage.py migrate
python manage.py seed_demo       # демонстрационные данные
python manage.py runserver
```

## Что можно улучшить дальше

- Закрыть оставшиеся потенциальные уязвимости (SEC-08 – SEC-12).
- Расширить автотесты, включая проверку числа SQL-запросов (`assertNumQueries`).
- Вынести `SECRET_KEY` в переменные окружения и отключить `DEBUG` для production.
